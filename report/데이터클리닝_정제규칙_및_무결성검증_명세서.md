# [데이터 엔지니어링] 수납·재정 데이터 정제규칙 및 무결성 검증 명세서 (SQL 포함)

본 문서는 **1,152만 건 원천 EMR 데이터 환경에서 수납(`payments`), 진료(`encounters`), 처방(`encounter_services`) 간 무결성을 확보하기 위해 적용한 핵심 정제규칙, 3단계 예외 격리 체계, 그리고 조인 팽창(Fan-out)을 방지하는 절차적 SQL 뷰 구현 내역**을 정리한 엔지니어링 명세서입니다.

---

## 1. 데이터 거버넌스 및 무결성 보장 원칙 (가정 · 구현 · 근거)

### 1.1 전처리 및 분석에 앞서 중복 처리와 예외 처리를 왜 먼저 수행하는가?
* **가정 (Premise)**:
  모든 통계 집계와 분석 모델은 '입력된 데이터 1행이 현실 세계의 유효한 1건의 사건'이라는 전제하에 작동합니다. 만약 네트워크 통신 재전송에 의한 중복 행(Duplication)이나 참조 무결성이 단절된 고아 레코드(Orphan)가 잔존한 상태에서 스케일링, 결측치 대체, 진료비 합산 등 전처리를 수행하면, 집계 분모와 분자가 모두 오염되어 모델 왜곡 및 심각한 데이터 누수(Data Leakage)가 발생합니다.
* **구현 (Implementation)**:
  전처리 및 분석 파이프라인의 최전방에 **'Zero-Drop 무손실 데이터 품질 게이트(DQ Gate)'**를 배치하여, 원천 데이터의 중복 행(`*_excluded`)과 필수 제약 위반 행(`*_quarantine`)을 먼저 분리 격리한 후 순수 모집단에 대해서만 정제 및 분석을 수행하도록 절차를 표준화했습니다.
* **근거 (Evidence)**:
  외래 EMR 데이터는 `접수 1건 ➔ 수납 2건(분할) ➔ 처방 3건`의 계층 구조를 가집니다. 만약 상위 접수·진료의 중복/결함을 먼저 제거하지 않으면, 하위 수납액과 처방액이 카테시안 곱으로 2배~6배 증폭되는 데이터 왜곡(Fan-out)이 발생함을 입증하였으며, 게이트웨이 선행 격리를 통해 496,863건의 순수 진료 모수를 확정했습니다.

### 1.2 격리 규칙 세분화 체계: 결함 유형별 다단계 분리 원칙
* **가정 (Premise)**:
  데이터 결함은 단순한 이상치가 아니며, 구문 오류, 도메인 위반, 비즈니스 규칙 위반, 참조 계보 단절 등 발생 원인이 상이합니다. 이를 하나의 테이블에 뭉뚱그려 폐기하거나 알 수 없는 코드(`UNREGISTERED`)를 자의적으로 정상값(`PAYMENT`, `CARD`)으로 보정하면, 데이터 왜곡과 감사 추적성 상실을 초래합니다.
* **구현 (Implementation)**:
  결함 격리 체계를 3단계로 엄격히 세분화하고 자의적 변환 0건(Zero-Arbitrary Conversion)을 적용했습니다:
  1. **완전 중복 제외 (`*_excluded`)**: 전 컬럼 값이 동일하게 중복 전송된 행(수납 7,501건)을 클린 DB 및 분석 대상에서 분리.
  2. **원천 구조 결함 격리 (`*_quarantine`)**: PK 중복, 더미 센티널 키(`_999999999`), 음수 금액, 유효하지 않은 날짜(2월 30일 등), 표준 사전에 없는 미상 코드(`UNREGISTERED` 22,503건)를 원본 문자열과 파일명/라인 번호 그대로 격리 원장에 보존.
  3. **연쇄 격리 (`reclean_quarantine`)**: 상위 부모 결함에 의해 참조가 끊어진 2차 고아 레코드(약 280만 건, 결제 67.9만 건 포함)를 별도 격리하여 클린 DB의 19개 물리 FK 무결성 100%를 달성.
* **근거 (Evidence)**:
  `quarantine_payments.csv` 및 `team3_medallion_dq` 스키마에 `_file`, `_csv_line`, `_issues`(세미콜론 복수 사유 코드)를 함께 기록하여, 금융 감사 수준의 데이터 계보(Lineage) 추적성을 100% 확보했습니다.

### 1.3 중복 식별자 및 다대다 조인 시 금액 팽창(Fan-out) 방지 원칙
* **가정 (Premise)**:
  완료 진료 1건에 N건의 수납 거래(73.2만 건)와 M건의 처방 내역(149만 건)이 연결되는 1:N:M 다대다 관계에서, 도메인 테이블을 직접 조인(`encounters JOIN payments JOIN services`)하면 카테시안 곱(Cartesian Product)이 발생하여 진료비와 수납액이 수 배로 부풀려지는 Fan-out 오류가 필연적으로 발생합니다.
* **구현 (Implementation)**:
  **'Silver Layer 그레인 단위 선(先)집계 (Pre-aggregation at Grain Level)'** 전략을 설계·구현했습니다.
  - `baek_silver_payment_totals`: `GROUP BY encounter_id`를 통해 진료당 1행으로 결제액과 환불액 선집계
  - `baek_silver_service_totals`: `GROUP BY encounter_id`를 통해 진료당 1행으로 처방 총액 선집계
  - `baek_gold_encounter_finance`: 선집계된 뷰들을 진료 본체에 **1:1 보장 LEFT JOIN**으로 결합
* **근거 (Evidence)**:
  496,863건의 완료 진료 전수에 대해 단 1원의 조인 팽창 없이 `순청구액(193.82억 원) = 순수납액(193.82억 원)`으로 재정 대사 차액 **0원 (100.0% 정합성)**을 입증했습니다.

---

### 1.4 부모 레코드 결함 시 하위 계보 처리: Cascade 연쇄 격리와 Zero-Drop 보존
* **가정 (Premise)**:
  상위 부모 레코드(`encounters`, 207,473건)가 결함으로 격리될 때, 하위 자식 레코드(`payments` 679,530건, `encounter_services` 942,000건)는 자체 값에는 이상이 없더라도 참조 대상이 없는 고아(Orphan) 상태가 됩니다. 이때 Restrict(부모 격리 차단)를 적용하면 클린 DB에 결함이 잔존하고, 단순 Drop(삭제)을 적용하면 실제 금전 거래 기록이 유실되는 딜레마가 발생합니다.
* **구현 (Implementation)**:
  클린 DB 분석 환경에서는 **Cascade 연쇄 격리**를, 재무 감사 추적 환경에서는 **Zero-Drop 무손실 보존**을 결합 적용했습니다:
  - **Clean DB (`team3_medallion`)**: 상위 부모 결함 시 하위 고아 거래도 Clean DB에서 연쇄 제외(Cascade)하여 물리 외래키 참조 무결성을 100% 확보.
  - **Audit DB (`team3_medallion_dq`)**: 연쇄 격리된 결제 679,530건을 `reclean_quarantine` 테이블에 원본 그대로 보존(Zero-Drop)하여 사후 감사 및 소명 큐로 관리.
* **근거 (Evidence)**:
  Clean DB 내 19개 물리 외래키(FK) 참조 무결성 100.0% 달성 (`02_scan.txt` 검증) 및 금전 거래 데이터 영구 유실 0건을 동시에 달성했습니다.

### 1.5 아키텍처 선택: 객체지향 인메모리 병목 극복을 위한 절차적 뷰(SQL View) 활용
* **가정 (Premise)**:
  1,152만 건에 달하는 대용량 엔터프라이즈 EMR 환경에서 복잡한 계층형 엔티티 매핑을 순수 애플리케이션 레벨의 객체지향(OOP) 모델이나 ORM으로 메모리에 올려 처리하려 할 경우, 대량 객체 생성 오버헤드, 가비지 컬렉션(GC) 지연, 메모리 스왑 및 트랜잭션 타임아웃이 발생하여 실무적 연산이 불가능해집니다.
* **구현 (Implementation)**:
  **'이론적인 객체 모델링의 이상보다, 대용량 데이터를 메모리 터짐 없이 1초 만에 검증해 내는 실무적 연산 효율성과 성능을 위해 절차적 뷰 활용을 선택했습니다.'**
  원천 데이터를 Read-Only 불변(Immutability) 트랜잭션으로 보호한 상태에서 MySQL 8.4 엔진 네이티브 절차적 뷰(Silver 7종 ➔ Gold 3종) 모델링을 구축했습니다.
* **근거 (Evidence)**:
  DB 엔진 내부의 B-Tree 인덱스와 쿼리 옵티마이저를 활용하여 496,863건의 3자 재정 대사 마트(`baek_gold_encounter_finance`) 조회를 **1초 이내(0.8~1.2초)**에 안정적으로 완료하도록 성능과 무결성을 동시에 입증했습니다.

## 3. 핵심 SQL 쿼리 세트 (1:N 조인 뻥튀기 방지 및 1초 대사)

### ① [수납 선집계 뷰] 1:N 조인 팽창 방지 쿼리 (`baek_silver_payment_totals`)
> 진료(`encounter_id`) 1건에 결제·환불 거래가 2~3건 분할되어 있어도, 본 뷰에서 진료당 1행으로 먼저 집계합니다.
```sql
CREATE OR REPLACE VIEW baek_silver_payment_totals AS
SELECT
    encounter_id,
    -- 결제(PAYMENT) 건수와 금액 선집계
    COUNT(CASE WHEN transaction_type = 'PAYMENT' THEN 1 END) AS payment_rows,
    COALESCE(SUM(CASE WHEN transaction_type = 'PAYMENT' THEN amount ELSE 0 END), 0) AS total_payment_amount,
    
    -- 환불(REFUND) 건수와 금액 선집계
    COUNT(CASE WHEN transaction_type = 'REFUND' THEN 1 END) AS refund_rows,
    COALESCE(SUM(CASE WHEN transaction_type = 'REFUND' THEN amount ELSE 0 END), 0) AS total_refund_amount,
    
    -- 진료별 순수납액 (결제액 - 환불액) 사전 계산
    COALESCE(SUM(CASE WHEN transaction_type = 'PAYMENT' THEN amount ELSE 0 END), 0)
    - COALESCE(SUM(CASE WHEN transaction_type = 'REFUND' THEN amount ELSE 0 END), 0) AS net_payment_amount
FROM team3_medallion.payments
GROUP BY encounter_id; -- ★ 핵심: 진료당 1행으로 축약하여 카테시안 곱 원천 차단
```

---

### ② [처방 선집계 뷰] 1:M 처방 상세 합산 쿼리 (`baek_silver_service_totals`)
> 진료 1건에 처방(`encounter_services`)이 평균 3건 붙어 있어도, 본 뷰에서 진료당 1행으로 합산합니다.
```sql
CREATE OR REPLACE VIEW baek_silver_service_totals AS
SELECT
    encounter_id,
    COUNT(*) AS service_rows,
    -- 단가 * 수량 - 할인액으로 처방 총진료비 선집계
    COALESCE(SUM(ROUND(unit_price * quantity - discount, 2)), 0) AS calculated_service_total
FROM team3_medallion.encounter_services
GROUP BY encounter_id; -- ★ 핵심: 진료당 1행으로 축약
```

---

### ③ [환불 원결제 추적 뷰] 자기참조 외래키 검증 (`baek_silver_refund_links`)
> 환불 거래가 과거 원결제(`original_payment_id`)와 올바르게 매핑되는지 검증합니다.
```sql
CREATE OR REPLACE VIEW baek_silver_refund_links AS
SELECT
    r.payment_id AS refund_payment_id,
    r.encounter_id,
    r.amount AS refund_amount,
    r.transacted_at AS refund_time,
    r.original_payment_id,
    p.amount AS original_amount,
    p.transacted_at AS original_time,
    CASE
        WHEN r.original_payment_id IS NULL THEN 'MISSING_ORIGINAL_KEY'
        WHEN p.payment_id IS NULL THEN 'ORIGINAL_NOT_FOUND'
        WHEN p.transaction_type <> 'PAYMENT' THEN 'ORIGINAL_NOT_A_PAYMENT'
        WHEN p.encounter_id <> r.encounter_id THEN 'ENCOUNTER_MISMATCH'
        WHEN r.transacted_at < p.transacted_at THEN 'REFUND_PRECEDES_PAYMENT'
        ELSE 'VALID_LINK'
    END AS link_status
FROM team3_medallion.payments r
LEFT JOIN team3_medallion.payments p ON r.original_payment_id = p.payment_id
WHERE r.transaction_type = 'REFUND';
```

### ④ [최종 골드 마트] 절차적 뷰 1:1 결합 및 1초 대사 (`baek_gold_encounter_finance`)
> 선집계된 Silver 뷰들을 진료 본체에 1:1 LEFT JOIN하여 496,863건에 대해 단 1원의 왜곡 없이 대사 차액 0원을 입증합니다.
```sql
CREATE OR REPLACE VIEW baek_gold_encounter_finance AS
SELECT
    e.encounter_id,
    e.patient_id,
    e.started_at,
    e.net_charge,               -- EMR 원천 순청구액
    p.total_payment_amount,     -- ①번 뷰: 총 결제액
    p.total_refund_amount,      -- ①번 뷰: 총 환불액
    p.net_payment_amount,       -- ①번 뷰: 순수납액 (결제 - 환불)
    s.calculated_service_total, -- ②번 뷰: 처방 합산액
    
    -- 재정 대사 차액 검증 (순수납액 - 순청구액)
    COALESCE(p.net_payment_amount, 0) - e.net_charge AS transaction_gap,
    
    -- 대사 상태 판정
    CASE 
        WHEN COALESCE(p.net_payment_amount, 0) - e.net_charge = 0 THEN 'MATCH'
        ELSE 'MISMATCH'
    END AS reconciliation_status
FROM team3_medallion.encounters e
LEFT JOIN baek_silver_payment_totals p ON e.encounter_id = p.encounter_id   -- 1:1 결합 (조인 팽창 0건)
LEFT JOIN baek_silver_service_totals s ON e.encounter_id = s.encounter_id;  -- 1:1 결합 (조인 팽창 0건)
```
