# [데이터 엔지니어링] 수납·재정 데이터 정제규칙 및 무결성 검증 명세서 (SQL 포함)

본 문서는 **1,152만 건 원천 EMR 데이터 환경에서 수납(`payments`), 진료(`encounters`), 처방(`encounter_services`) 간 무결성을 확보하기 위해 적용한 핵심 정제규칙, 3단계 예외 격리 체계, 그리고 조인 팽창(Fan-out)을 방지하는 절차적 SQL 뷰 구현 내역**을 정리한 엔지니어링 명세서입니다.

---

## 1. 정제 및 예외 처리 원칙 (심사위원 질의 대응 및 엔지니어링 근거)

### Q1. "전처리나 분석보다 '중복 처리'와 '예외 처리'를 왜 먼저 수행했는가?"
- **핵심 키워드**: 데이터 신뢰성 보장(Data Reliability Gate), 통계적 왜곡 및 조인 팽창 방지(Fan-out Preemption)
- **배경 및 원인**: 중복 데이터나 결함 데이터가 섞여 있는 상태에서 진료 건수, 매출액, 환자 수를 집계하면 분모와 분자가 모두 오염됩니다. 특히 외래 EMR은 `접수 1건 ➔ 수납 2건(분할) ➔ 처방 3건`이 복합 연결되어 있어, 상위 레코드가 중복되면 하위 거래액이 2배, 4배로 왜곡(Fan-out)됩니다.
- **방어 답변**:
  > "분석 모델이나 전처리는 '데이터 1행이 1개의 유효한 사실'이라는 전제하에 작동합니다. 만약 네트워크 오류로 동일 환자의 접수·수납이 중복 적재되었거나, 필수 외래키가 없는 고아 레코드가 남아있다면, 어떤 정밀한 분석을 해도 결과는 왜곡된 허수가 됩니다. 그래서 분석에 앞서 'Zero-Drop 무손실 격리 게이트'를 통해 중복과 예외를 먼저 걷어내고 모집단의 순도를 확보했습니다."

---

### Q2. "격리 규칙 세분화 관점에서 실제로 구현한 체계는 무엇인가?"
- **핵심 키워드**: 다단계 다차원 결함 분류(Multi-tiered Fault Segregation), 격리 사유 계보 보존(Quarantine Lineage Tracking)
- **실제 DB 구현 근거**: `team3_medallion_dq` 스키마에 단순히 뭉뚱그려 넣은 것이 아니라, 테이블별로 격리 사유를 명시하여 3단계로 분리 보존했습니다.
  1. **완전 중복 제외 (`*_excluded`)**: 전 컬럼 값이 동일하게 중복 전송된 행(예: `payments` 7,501건)은 클린 DB와 분석 대상에서 분리.
  2. **원천 구조 결함 격리 (`*_quarantine`)**: PK 중복, 더미 센티널 키(`_999999999`), 음수 금액, 시간 역전(진료 시작 > 종료) 등 원천 레코드 자체의 오류를 격리 (예: `payments` 88,006건, `encounters` 241,361건).
  3. **연쇄 격리 (`reclean_quarantine`)**: 데이터 자체는 유효하지만 상위 부모(접수/진료)가 격리되어 참조가 끊어진 2차 고아 레코드(약 280만 건, 결제 67.9만 건 포함)를 별도 격리하여 클린 DB의 19개 물리 FK 무결성 100%를 달성했습니다.

### Q3. "중복 처리 및 테이블 조인 시 뻥튀기를 어떻게 방지했는가?"
- **핵심 키워드**: 그레인 단위 사전 집계(Pre-aggregation at Grain Level), 카테시안 곱 증폭 억제(Fan-out Mitigation)
- **실제 SQL 구현 근거**:
  - `baek_silver_payment_totals`: `GROUP BY encounter_id`
  - `baek_silver_service_totals`: `GROUP BY encounter_id`
- **방어 답변**:
  > "환자나 진료 코드에 대해 여러 건의 처방(encounter_services, 149만 건)과 수납(payments, 73.2만 건)이 연결될 때, 테이블을 직접 조인(`encounters JOIN payments JOIN services`)하면 1:N:M 다대다 곱(Cartesian Product)이 발생하여 진료비와 수납액이 수 배로 뻥튀기됩니다. 이를 막기 위해 저희는 조인 전에 반드시 각 도메인을 `encounter_id` 단위로 선(先)집계했습니다. 즉, 수납은 수납대로 진료별 합계를 내고, 처방은 처방대로 합계를 낸 뒤, 최종 골드 마트에서 진료 본체와 1:1 LEFT JOIN을 수행하여 **단 1원의 금액 왜곡 없는 100% 대사 일치(차액 0원)**를 입증했습니다."

---

### Q4. "부모가 격리되면 연결된 하위 자료는 어떤 순서로 격리되는가? Cascade와 Restrict의 차이는?"
- **핵심 키워드**: 하향식 계보 전파(Top-down Lineage Cascade), 무손실 참조 격리(Zero-Drop Restrictive Isolation)
- **실제 업무 순서**: `병원/환자 ➔ clinic_sessions ➔ appointment_slots ➔ checkins ➔ encounters ➔ encounter_services / payments`
- **방어 답변**:
  > "EMR의 진료 라이프사이클에 맞추어 하향식(Top-Down) 순서로 격리됩니다.
  > 
  > 1. **왜 Restrict가 아닌 Cascade를 택했는가?**: 원칙적인 DB 트랜잭션에서는 자식 데이터(결제 내역)가 있으면 부모를 격리하지 못하게 막는(Restrict) 것이 안전하지만, 그렇게 하면 상위 결함(가짜 환자, 미등록 세션) 때문에 클린 DB 전체의 신뢰도가 무너집니다. 따라서 클린 DB(`team3_medallion`)의 19개 물리 FK 무결성 100%를 지키기 위해 자식 데이터까지 연쇄적으로 격리하는 Cascade 전략을 택했습니다.
  > 2. **그럼 자식 결제 데이터는 버렸는가?**: 아닙니다. 결제는 실제 금전 기록이므로 영구 삭제(Drop)하지 않고, 감사 추적용 스키마(`team3_medallion_dq`)의 `reclean_quarantine` 테이블에 원본 그대로 보존(Zero-Drop)하여 차후 역추적이 가능하게 설계했습니다."

---

### Q5. "객체지향(OOP)으로 하려다 막히면 왜 절차지향(SQL View)으로 구성했는가?"
- **핵심 키워드**: 인메모리 ORM 병목 해소, DB 엔진 네이티브 최적화(Engine-native Execution Plan)
- **방어 답변**:
  > **"이론적인 객체 모델링의 이상보다, 대용량 데이터를 메모리 터짐 없이 1초 만에 검증해 내는 실무적 연산 효율성과 성능을 위해 절차적 뷰 활용을 선택했습니다."**
  > 
  > 파이썬 객체지향(OOP) 모델이나 ORM으로 1,150만 건의 계층적 연쇄 격리와 대사를 메모리에 올려 처리하려 하면, 객체 생성 오버헤드와 메모리 스왑으로 인해 시스템이 멈춥니다. 반면 절차적 SQL 뷰(Silver 7종 ➔ Gold 3종) 모델링을 적용하면, MySQL 8.4 데이터베이스 엔진 자체의 B-Tree 인덱스와 조인 최적화(Optimizer)를 그대로 활용할 수 있습니다.

## 3. 핵심 SQL 쿼리 세트 (1:N 조인 뻥튀기 방지 및 1초 대사)

### ① [수납 선집계 뷰] 1:N 조인 팽창 방지 쿼리 (`baek_silver_payment_totals`)
> 진료(`encounter_id`) 1건에 결제·환불 거래가 2~3건 분할되어 있어도, 본 뷰에서 진료당 1행으로 먼저 집계합니다.
```sql
CREATE OR REPLACE VIEW baek_silver_payment_totals AS
SELECT
    encounter_id,
    -- 결제(PAYMENT) 건수와 금액 선집계
    COUNT(CASE WHEN transaction_type = 'PAYMENT' THEN 1 END) AS payment_rows,
    COALESCE(SUM(CASE WHEN transaction_type = 'PAYMENT' THEN amount ELSE 0 END), 0) AS total_payment_amount,
    
    -- 환불(REFUND) 건수와 금액 선집계
    COUNT(CASE WHEN transaction_type = 'REFUND' THEN 1 END) AS refund_rows,
    COALESCE(SUM(CASE WHEN transaction_type = 'REFUND' THEN amount ELSE 0 END), 0) AS total_refund_amount,
    
    -- 진료별 순수납액 (결제액 - 환불액) 사전 계산
    COALESCE(SUM(CASE WHEN transaction_type = 'PAYMENT' THEN amount ELSE 0 END), 0)
    - COALESCE(SUM(CASE WHEN transaction_type = 'REFUND' THEN amount ELSE 0 END), 0) AS net_payment_amount
FROM team3_medallion.payments
GROUP BY encounter_id; -- ★ 핵심: 진료당 1행으로 축약하여 카테시안 곱 원천 차단
```

---

### ② [처방 선집계 뷰] 1:M 처방 상세 합산 쿼리 (`baek_silver_service_totals`)
> 진료 1건에 처방(`encounter_services`)이 평균 3건 붙어 있어도, 본 뷰에서 진료당 1행으로 합산합니다.
```sql
CREATE OR REPLACE VIEW baek_silver_service_totals AS
SELECT
    encounter_id,
    COUNT(*) AS service_rows,
    -- 단가 * 수량 - 할인액으로 처방 총진료비 선집계
    COALESCE(SUM(ROUND(unit_price * quantity - discount, 2)), 0) AS calculated_service_total
FROM team3_medallion.encounter_services
GROUP BY encounter_id; -- ★ 핵심: 진료당 1행으로 축약
```

---

### ③ [환불 원결제 추적 뷰] 자기참조 외래키 검증 (`baek_silver_refund_links`)
> 환불 거래가 과거 원결제(`original_payment_id`)와 올바르게 매핑되는지 검증합니다.
```sql
CREATE OR REPLACE VIEW baek_silver_refund_links AS
SELECT
    r.payment_id AS refund_payment_id,
    r.encounter_id,
    r.amount AS refund_amount,
    r.transacted_at AS refund_time,
    r.original_payment_id,
    p.amount AS original_amount,
    p.transacted_at AS original_time,
    CASE
        WHEN r.original_payment_id IS NULL THEN 'MISSING_ORIGINAL_KEY'
        WHEN p.payment_id IS NULL THEN 'ORIGINAL_NOT_FOUND'
        WHEN p.transaction_type <> 'PAYMENT' THEN 'ORIGINAL_NOT_A_PAYMENT'
        WHEN p.encounter_id <> r.encounter_id THEN 'ENCOUNTER_MISMATCH'
        WHEN r.transacted_at < p.transacted_at THEN 'REFUND_PRECEDES_PAYMENT'
        ELSE 'VALID_LINK'
    END AS link_status
FROM team3_medallion.payments r
LEFT JOIN team3_medallion.payments p ON r.original_payment_id = p.payment_id
WHERE r.transaction_type = 'REFUND';
```

### ④ [최종 골드 마트] 절차적 뷰 1:1 결합 및 1초 대사 (`baek_gold_encounter_finance`)
> 선집계된 Silver 뷰들을 진료 본체에 1:1 LEFT JOIN하여 496,863건에 대해 단 1원의 왜곡 없이 대사 차액 0원을 입증합니다.
```sql
CREATE OR REPLACE VIEW baek_gold_encounter_finance AS
SELECT
    e.encounter_id,
    e.patient_id,
    e.started_at,
    e.net_charge,               -- EMR 원천 순청구액
    p.total_payment_amount,     -- ①번 뷰: 총 결제액
    p.total_refund_amount,      -- ①번 뷰: 총 환불액
    p.net_payment_amount,       -- ①번 뷰: 순수납액 (결제 - 환불)
    s.calculated_service_total, -- ②번 뷰: 처방 합산액
    
    -- 재정 대사 차액 검증 (순수납액 - 순청구액)
    COALESCE(p.net_payment_amount, 0) - e.net_charge AS transaction_gap,
    
    -- 대사 상태 판정
    CASE 
        WHEN COALESCE(p.net_payment_amount, 0) - e.net_charge = 0 THEN 'MATCH'
        ELSE 'MISMATCH'
    END AS reconciliation_status
FROM team3_medallion.encounters e
LEFT JOIN baek_silver_payment_totals p ON e.encounter_id = p.encounter_id   -- 1:1 결합 (조인 팽창 0건)
LEFT JOIN baek_silver_service_totals s ON e.encounter_id = s.encounter_id;  -- 1:1 결합 (조인 팽창 0건)
```
