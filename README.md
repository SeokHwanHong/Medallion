# 1석 4조 · 외래 EMR 데이터 분석 프로젝트

> **자원은 충분한데 병원은 왜 멈추는가?**
> 데이터 기반 의료 자원 불균형 해소 및 외래 프로세스 개선

외래 EMR의 예약·접수·진료·수납 데이터를 정제하고 연결해, 환자의 진료 과정과 병원 운영을 네 가지 관점에서 분석하는 1석 4조(팀 3)의 데이터 엔지니어링·분석 프로젝트입니다.

## 1. 개요

### 1.1 프로젝트 배경과 목적

병원 운영을 이해하려면 의료기관·의료진의 규모뿐 아니라 환자가 언제 도착하고, 진료와 수납으로 어떻게 이어지는지도 함께 살펴봐야 합니다. 원천 시스템별로 분산된 기록과 단계별로 분리된 집계만으로는 외래 전 과정의 문제를 파악하기 어렵습니다.

이 프로젝트는 병원 기준정보부터 예약, 접수, 진료, 결제·환불까지 연결되는 데이터를 바탕으로 **운영 현황을 정량적으로 파악하고 우선 점검할 범위와 개선 방향을 제안**하는 것을 목적으로 합니다.

### 1.2 대주제와 네 가지 분석 관점

**대주제: 데이터 기반 의료 자원 불균형 해소 및 외래 프로세스 최적화**

| 관점 | 소주제 | 확인할 내용 | 개선 검토 방향 |
| --- | --- | --- | --- |
| 인프라 | 레거시 원천 시스템 A/B 품질 비교와 통합 | 시스템별 품질 차이, 교차 이용 환자, 기준정보의 일관성 | 환자·코드 기준정보 통합과 검증 |
| 접수 | 진료과·시간대별 현장접수 불가 패턴 분석을 통한 사전 방문 안내 개선 | 접수불가 규모·비율·시간대별 차이와 반복성 | 발생 규모가 큰 반복 구간의 접수 정책·사전 안내 점검 |
| 진료 | 병원별 환자 밀집도 분석을 통한 의사 진료 배치 최적화 | 병원·진료과별 환자 규모와 의사 배치의 편차 | 의료 자원 배치 대안 검토 |
| 수납 | 진료 후 결제·환불 패턴 분석을 통한 병원 재정 관리 및 수납 업무 효율화 방향 | 청구·결제·환불의 연결과 대사, 복수거래의 구성 | 진료 단위 통합 확인과 재확인 절차 검토 |

네 관점은 **기준정보 통합 → 접수 → 진료 → 수납**이라는 외래 진료 흐름으로 연결됩니다. 개별 지표를 곧바로 운영 원인으로 단정하지 않고, 관측 사실과 개선 제안을 구분합니다.

## 2. 데이터

### 2.1 데이터 파이프라인

![외래 EMR 데이터 파이프라인](docs/assets/emr-data-pipeline.png)

원천 A/B 데이터를 보존하고 품질을 점검한 뒤, 정제·격리 결과를 바탕으로 네 소주제를 분석합니다.

| 단계 | 처리 내용 | 코드·산출물 |
| --- | --- | --- |
| Bronze | 원본 CSV 보존, 원천별 결측·중복·코드 프로파일링 | `data/input/`, A/B 프로파일링 코드 |
| 정제·검증 | 키·코드 표준화, 시간·참조·금액 규칙 검증, 정상·격리·제외 분리 | `data/cleaning/`, `data/output/` |
| Silver | 정제 DB 조회, 분석용 참조 연결과 선집계 | `team3_medallion`, `team3_medallion_dq`, 수납 Silver 뷰 |
| 주제별 분석 | A/B 비교, 현장접수 패턴, 의사 배치, 수납 대사·업무 복잡도 | `data_analysis/` |
| 결과 전달 | 도표·대시보드·PDF·발표자료 | `data_visualization/`, `report/` |

**구현 범위:** 그림의 점선은 DB 적재·통합 단계입니다. 저장소의 일부 노트북은 CSV 출력까지만 수행하며 전체 단계가 하나의 실행기로 자동 연결된 것은 아닙니다. 수납 영역에는 실제 Silver·Gold 뷰 SQL이 있고, 다른 주제는 조회 결과와 CSV·JSON 기반 집계를 활용합니다. 격리 기록은 대사 보류의 근거로 참조할 수 있지만 정상 거래로 합산하지 않습니다.

### 2.2 데이터의 성격과 구조

수도권 종합병원 환경을 재현한 **실습용 합성 외래 EMR 데이터**를 사용합니다. 실제 환자·병원의 운영 성과로 일반화할 수 없으며, 생성 규칙이 분포와 반복 패턴에 영향을 줄 수 있습니다.

| 항목 | 발표자료에 기재된 범위 |
| --- | --- |
| 원천 데이터 규모 | 약 1,157만 건 |
| 데이터 구조 | 17개 테이블, 119개 컬럼 |
| 의료기관 | 490개소 |
| 의료진 | 전문의 4,748명 |
| 분석 기간 | 2023년 1월~2025년 12월 |
| 정제 데이터 스키마 | `team3_medallion` |
| 품질 검토·격리 스키마 | `team3_medallion_dq` |

위 규모는 최종 발표자료의 원천 개요입니다. 저장소의 정제·분석 보고서는 원천 11,522,242행 및 일부 분석에서 유효 병원 485개를 사용하므로, 발표 개요의 490개와 동일한 모집단으로 취급하지 않습니다. 소주제별 지표는 해당 기간·분모·스냅샷을 따릅니다.

#### 주요 도메인과 테이블

| 도메인 | 주요 테이블 | 주요 정보 |
| --- | --- | --- |
| 의료기관·의료진 | `hospitals`, `hospital_departments`, `departments`, `doctors`, `doctor_assignments` | 병원·진료과 기준정보, 의사 소속·배치와 유효기간 |
| 외래 세션·예약 | `clinic_sessions`, `appointment_slots`, `appointments`, `appointment_events` | 운영 세션, 예약 슬롯, 예약 상태와 변경 이력 |
| 접수·진료 | `patients`, `checkins`, `encounters`, `encounter_services` | 환자 기준정보, 도착·접수 결과, 진료 시각, 서비스 상세 |
| 서비스·수납 | `service_catalog`, `payments`, `refunds`, `ext_code_dictionary` | 서비스 가격 버전, 결제·환불, 원천 코드 매핑 |

테이블별 키와 상세 연결 관계는 [ERD 안내](hospital_erd_guide.html)에서 확인할 수 있습니다.

### 2.3 데이터 정제 방법

명세서와 ERD의 키·자료형·업무 규칙을 기준으로 데이터를 점검합니다. 복구 가능한 표기 차이는 표준화하고, 근거가 부족하거나 참조 관계를 확인할 수 없는 기록은 정상 데이터에 억지로 포함하지 않습니다.

| 점검 영역 | 주요 확인 사항 | 처리 원칙 |
| --- | --- | --- |
| 식별자·참조 무결성 | 기본키 중복·충돌, 필수키 결측, 부모 레코드 존재 여부 | 동일 내용 중복과 키 충돌을 구분하고 검토·제외 사유 기록 |
| 날짜·시간 정합성 | 도착·접수·진료 시각 순서, 유효한 날짜와 세션 범위 | 명세서가 허용하는 표기만 표준화하고 불가능한 값은 검토 대상으로 분리 |
| 기준정보 표준화 | 성별·예약 채널·서비스 분류 등 원천 코드 차이 | 명시적 매핑으로 통합하고 미등록·충돌 코드는 별도 확인 |
| 진료·금액 교차검증 | 접수 결과와 진료 연결, 서비스 단가·상세합, 결제·환불 관계 | 독립된 근거를 대조하고 상충하거나 불충분한 값은 임의 보정하지 않음 |
| 운영·중복 거래 점검 | 비정상 운영 시각, 중복 예약·거래, 업무상 허용 범위 | 업무 규칙에 따라 분류하고 검토 대상과 중복 제외 이력 보존 |

발표자료는 이러한 정제 범주를 **16대 무결성 정제 로직**으로 요약합니다. 저장소의 노트북별 세부 판정과 출력은 각 코드의 구현을 기준으로 확인합니다.

#### 사용 도구

| 도구 | 역할 |
| --- | --- |

| SQLAlchemy | 발표자료에 제시된 DB 연계·적재 도구 |

### 2.4 정제 결과와 정합성 확인

정제 결과는 **정상(Clean), 검토·격리(Quarantine), 완전 중복 제외(Excluded)**로 구분합니다. 전체 원천 건수와 각 분류의 합계를 대사하고, 부모 레코드 격리가 하위 거래에 미치는 영향도 확인합니다.

최종 발표자료와 저장소의 정제·검증 보고서에는 서로 다른 집계값이 있습니다. 아래 수치를 하나의 정제 전후 비교로 섞지 않습니다.

| 항목 | 최종 발표자료 | develop 정제·검증 문서 |
| --- | ---: | ---: |
| 원천 전체 | 약 1,157만 건 | 11,522,242행 |
| 정제 encounters | 488,684건 | 496,863건 |
| 정제 encounter_services | 1,499,018건 | 1,490,589건 |
| 격리·제외 비중 | 임상 영역 약 30%로 요약 | 전체 누적 약 38.4%로 기재 |

격리율의 집계 범위가 다르고 다른 건수 차이는 이 문서 작성 시 DB를 재조회해 확정하지 않았습니다. 분석 결과에는 소주제별 보고서가 명시한 모집단을 사용합니다. 수납 분석은 진료 496,863건 기준이며, 현장접수 분석은 WALK_IN 298,257건 기준입니다.

- **참조 무결성:** 발표자료는 정제 DB의 19개 물리 외래키 참조 무결성 100%를 제시합니다. 모든 업무 규칙을 포괄하는 지표로 해석하지 않습니다.
- **중복 합산 방지:** 서비스·결제·환불을 업무 키 단위로 선집계해 일대다 조인 증폭을 방지합니다.
- **격리 사유 보존:** 상위 참조 오류·업무 규칙 위반·중복 제외를 구분하고 처리 근거를 기록합니다.
- **진단과 분석 분리:** 격리 연결 여부는 대사 보류를 판단하는 보조 근거이며 정상 거래로 복원하는 근거가 아닙니다.

## 3. 분석

### 3.1 대주제의 As-Is

외래 전주기에서 **기록의 분산, 접수불가의 구간별 차이, 의료진 배치 편차, 복수 수납 거래의 확인 부담**을 살펴봅니다. 정제 데이터의 관측 결과와 모형·시나리오에 따른 수치를 구분해 해석합니다.

| 영역 | 핵심 지표 | 해석 범위 |
| --- | --- | --- |
| A/B 시스템 | 예약 기록이 있는 고유 환자의 76.7%가 양쪽 시스템 병원을 이용 | 환자 연결과 기준정보 통합을 검토할 근거 |
| 현장접수 | WALK_IN 298,257건 중 REJECTED 73,471건, **24.63%** | 실제 헛걸음·접수불가 사유·안내 효과까지 뜻하지는 않음 |
| 의사 배치 | 보고서의 과밀·유휴 그룹 평균 부하 **279.3 대 34.7, 약 8.0배** | 해당 집계·분류 기준의 차이이며 보편적 적정 진료량 기준은 아님 |
| 수납 | 완료 진료의 복수거래 비중 **47.4%** | 거래 구성을 나타내며 실제 직원 작업시간은 별도 로그 필요 |

### 3.2 소주제별 결과와 개선 방향

#### ① 레거시 원천 시스템 A/B 품질 비교와 통합

- 시스템 자체 결함 건수의 차이는 분석 기준에서 5% 이내로, 한 시스템이 우월하다고 단정할 근거가 부족했습니다.
- 환자의 **76.7%**가 A/B 양쪽 시스템 병원을 이용하는 것으로 집계됐습니다.
- 원본 단가표의 오류 **7행**이 진료 서비스 **115,590줄**에 연결되는 파급을 확인했습니다. 원본 오류 파급과 정제 후 연결 검증은 별도 기준입니다.
- **To-Be:** 환자 식별체계·공통 기준정보를 통합하고 취소·노쇼 기록 시점의 정의를 일치시키는 방향을 제안합니다.

#### ② 진료과·시간대별 현장접수 불가 패턴 분석을 통한 사전 방문 안내 개선

전체 접수불가율은 **24.63%**, 진료과별 비율 범위는 **23.65~25.18%**였습니다. 진료과 평균 차이는 작지만, 도착 시간대로 나누면 일부 구간에서 약 50%의 불가율이 반복됐습니다.

같은 월·진료과 전체보다 불가율이 **5%p 이상 높은 달이 관측 월의 2/3 이상**인 구간을 찾고, 그중 접수불가 건수가 많은 네 구간을 우선 점검 대상으로 선정했습니다. 이는 분석상 기준이며 업무 표준·통계적 유의성 기준이 아닙니다.

| --- | ---: | ---: | ---: | ---: |
| 신경과 12시대 | 12,947 | 6,471 | 49.98% | 36/36 |
| 가정의학과 9시대 | 12,897 | 6,441 | 49.94% | 36/36 |
| 비뇨의학과 10시대 | 12,188 | 6,094 | 50.00% | 36/36 |
| 산부인과 13시대 | 11,969 | 5,990 | 50.05% | 36/36 |

네 구간의 접수불가는 **24,996건**, 전체 접수불가 기록의 **34.02%**입니다. 이는 기록의 포함 비중이며 예방 가능한 비율이나 회복할 환자 수가 아닙니다. 시간대는 실제 도착 시각이며 접수 마감 시각을 뜻하지 않습니다.

**To-Be:** 선정 구간의 실제 접수 정책을 병원별로 확인하고 기존 안내와 대조합니다. 누락·불명확한 안내가 확인되면 접수 조건과 공식 문의 경로를 보완합니다. 합성 자료의 0%·약 50% 반복을 실제 운영 원인이나 미래 위험률로 일반화하지 않습니다.

#### ③ 병원별 환자 밀집도 분석을 통한 의사 진료 배치 최적화

- 소주제 보고서는 병원·진료과 단위의 진료 규모를 배치 의사 수로 나누어 부하를 비교합니다.
- 보고서의 과밀 그룹은 평균 **279.3**, 유휴 그룹은 **34.7**로 약 **8.0배** 차이를 보였습니다. 원천 집계 기간의 지표를 별도 근거 없이 ‘하루 환자 수’로 환산하지 않습니다.
- **To-Be 시뮬레이션:** 동일 진료과의 유휴 인력을 재배치하는 가정에서 부하 **279.3 → 153.9**, 대기시간 **19.4분 → 11.0분**으로 제시됐습니다.
- 부하 **44.9%**, 대기시간 **43.2%** 감소는 보고서의 시뮬레이션 결과입니다. 실제 병원 적용 성과가 아니며 이동·협약·운영 비용까지 0원으로 검증한 것은 아닙니다.

## 4. 결론과 향후 과제

### 4.1 To-Be 실행 방향

1. **기준정보 정비:** 환자·진료과·서비스 코드와 원천 시스템의 상태 정의를 정렬합니다.
2. **우선 구간 점검:** 현장접수의 반복 고율 구간에서 실제 정책과 사전 안내의 일치 여부를 확인합니다.
3. **운영 대안 검토:** 의사 배치와 수납 확인 절차의 시나리오를 실제 제약·비용·작업 로그로 보완합니다.
4. **적용 후 평가:** 변경 내용·시점·노출·운영 조건을 기록해 제안 효과를 별도로 검증합니다.

### 4.2 한계

- **합성 데이터:** 생성 규칙이 분포와 반복 패턴을 만들 수 있어 실제 병원의 인과관계로 일반화할 수 없습니다.
- **집계 스냅샷:** 원천·1차 정제·연쇄 격리 후 데이터의 건수와 기관 수가 다릅니다. 소주제별 분모·기간을 유지해야 합니다.
- **원인 정보 부족:** 접수불가 사유·안내 노출·실제 직원 처리시간이 충분하지 않습니다.
- **운영 제약 미반영:** 환자 중증도, 의사 세부 전공·이동 비용, 병원별 정책을 보완해야 합니다.
- **구현과 계획 구분:** 실시간 EMR 연동, 동적 슬롯, AI 예측은 향후 검토 방향이며 현재 완성된 서비스가 아닙니다.

## 6. 실행 안내

### 공통 준비

- Python과 Jupyter 환경에서 테이블별 노트북의 입력 경로·의존 파일을 확인합니다.
- `hospital_명세서.xlsx`, ERD, [공통 규약](common_contract.md)을 함께 참고합니다.
- 필요한 패키지는 노트북의 import와 소주제별 `requirements.txt`를 기준으로 설치합니다. 저장소 전체를 자동 실행하는 단일 명령은 제공하지 않습니다.
- SQL 파일을 실행하기 전 내용을 확인합니다. 수납의 뷰 구성 SQL은 **CREATE VIEW 권한이 필요한 준비 작업**이며 조회 전용 SQL과 구분합니다.

### 현장접수 분석 재현 예시

01~03 조회 결과 CSV를 해당 분석 폴더에 준비한 뒤 프로젝트 루트에서 실행합니다.

```powershell
python -m pip install -r "data_visualization/진료과·시간대별 현장접수 불가 패턴 분석을 통한 사전 방문 안내 개선/requirements.txt"
python "data_analysis/진료과·시간대별 현장접수 불가 패턴 분석을 통한 사전 방문 안내 개선/analyze_walk_in.py"
python "data_visualization/진료과·시간대별 현장접수 불가 패턴 분석을 통한 사전 방문 안내 개선/visualize_walk_in.py"
```

분석 결과는 `analysis_results.json`, 도표는 PNG·PDF로 생성됩니다. 기존 출력은 자동 덮어쓰지 않으므로 재실행할 때 `--output` 또는 `--output-dir`로 다른 경로를 지정합니다. PDF 보고서 생성 코드는 검토된 입력 스냅샷 전용이므로 데이터 변경 시 문구·수치를 재검토해야 합니다.

수납 대시보드와 다른 소주제 실행 방법은 각 폴더의 안내 및 코드 인자를 참고하세요.
